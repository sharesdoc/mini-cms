# J-系统改进意见

> 提案性质：须用户明确发起或确认后方可实施（dev 铁律 0）。本轮不自动落实。

## P2 — 客户详情页对非管理员查看者脱敏 idcard
- 现状：`/api/customers/{id}` 对管理员与普通客户（查看自己直接下游）均返回完整 UserVO（含 idcard/phone/address）。
- 理由保留：CRM 语境下，下游是查看者的团队成员，查看联系方式符合「客户管理」业务；且拓展需目标尚无上级，属受控关系。
- 建议（如需更严）：普通客户查看下游详情时对 idcard 做掩码（如保留首末位），仅管理员可见完整身份证。
- 关联：REQ-NET-05（详情），隐私纵深防御。

## P2 — 管理员「回收站」浏览已删除客户
- 现状：伪删除后客户从全部列表/树/详情消失（符合「隐藏」），`restore` 接口只能按已知 ID 恢复。
- 建议：管理端客户列表增加「包含已删除」筛选，或在客户详情对 deleted 客户显示「恢复」按钮。
- 关联：REQ-ADM-01（伪删除可恢复，当前恢复能力存在但无浏览入口）。

## P3 — MyBatis 日志按环境隔离
- 现状：`application.yml` 的 `log-impl: StdOutImpl` 在生产输出冗长 SQL。
- 建议：迁到 `application-dev.yml`，生产 profile 关闭或改 SLF4J。

## P3 — 消息实时推送
- 现状：消息为拉取（前端进入会话时加载历史）。
- 建议（需求未要求实时）：引入 WebSocket/SSE 实现新消息推送与未读计数。
- 关联：范围外，需求仅要求纯文本消息收发。

## P3 — Token 持久化
- 现状：Token 内存存储，svc 重启失效（I-R1）。
- 建议：多实例部署时改 Redis 存储。
